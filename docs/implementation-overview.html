Linear: Plugin/MCP 통합 레포 출시

Membase Plugin/MCP 구현 개요

흩어져 있던 4개의 클라이언트 커넥터 레포를 하나의 공개 통합 레포로 합친 과정과 현재 구현 상태를 설명합니다. 근거 문서: docs/adr/0001~0003, docs/architecture.md, docs/north-star-readiness.md.

0. 먼저 알아두면 좋은 용어

MCP (Model Context Protocol)
AI 앱(Claude, Cursor 등)이 외부 도구·데이터에 접속할 때 쓰는 표준 프로토콜. "AI용 USB 포트"라고 생각하면 됩니다. Membase가 MCP 서버가 되고, AI 클라이언트가 거기 꽂혀서 기억 저장/검색 도구를 씁니다.
커넥터 (connector) / 어댑터 (adapter)
커넥터 = "이 AI 클라이언트를 Membase에 연결해 주는 것" 전체. 어댑터 = 그중 클라이언트마다 다른 부분(설정 파일 형식, 설치 경로 등)을 담당하는 코드 조각. 콘센트 모양이 나라마다 달라서 여행용 어댑터를 끼우는 것과 같은 개념입니다.
manifest (매니페스트)
플러그인의 "자기소개서" 파일. 이름, 버전, 제공하는 기능, 실행 방법 등을 적은 JSON/YAML 문서로, 클라이언트가 이걸 읽고 플러그인을 로드합니다.
ADR (Architecture Decision Record)
"아키텍처를 왜 이렇게 정했는지"를 남기는 짧은 결정 기록 문서. 나중에 "왜 이랬더라?"를 코드가 아니라 문서에서 찾을 수 있게 합니다. 이 레포의 ADR 0001이 전체 구조를 정한 문서입니다.
smoke test (스모크 테스트)
"전원 켰을 때 연기 안 나는지" 보는 수준의 얕고 빠른 기본 동작 확인. 세세한 로직 검증이 아니라 "설정이 만들어지고, 연결되고, 기본 흐름이 도는가"만 봅니다.
E2E (end-to-end) 테스트
부품 단위가 아니라 실제 사용자 경로 전체를 처음부터 끝까지 태워 보는 테스트. 여기서는 "기억을 저장하고 → 실제 서버를 거쳐 → 검색하면 나오는가"까지 확인합니다.
parity (패리티)
"동등함". 옛 레포가 하던 것을 새 레포도 빠짐없이 똑같이 하는지 비교하는 작업. "패리티 가드"는 그 동등함이 깨지면 검사를 실패시키는 스크립트입니다.
가드 (guard)
정해 둔 규칙이 깨졌는지 자동으로 검사해서, 깨졌으면 빌드/체크를 실패시키는 스크립트. 사람이 매번 눈으로 확인하는 대신 기계가 막아줍니다.
redaction (리댁션)
로그나 진단 출력에서 비밀값(API 키 등)을 ****처럼 가려서 내보내는 것. 실수로 비밀이 화면·로그에 찍히는 사고를 막습니다.
stdio vs HTTP (MCP 전송 방식)
MCP 서버와 대화하는 두 가지 통로. stdio는 내 컴퓨터에서 프로그램을 직접 실행해 표준입출력으로 대화(로컬 실행), HTTP는 인터넷 주소로 원격 서버에 접속. 이 레포에서 Claude만 stdio(플러그인에 서버가 동봉됨)이고, Cursor·Hermes·OpenClaw의 MCP 설정은 전부 원격 HTTP (mcp.membase.so)를 씁니다.
OAuth / client_credentials
OAuth는 비밀번호를 직접 주지 않고 "허가 토큰"을 발급받는 로그인 표준. 보통 브라우저 로그인 화면이 뜹니다. client_credentials는 그중 사람 없이 프로그램(CI 등)이 자체 자격증명으로 토큰을 받는 방식 — 그래서 "브라우저 없이(headless)" 자동 테스트가 가능합니다.
CI (Continuous Integration)
코드를 push할 때마다 GitHub이 자동으로 빌드·테스트를 돌려주는 것 (여기서는 GitHub Actions). "CI 그린" = 그 자동 검사가 전부 통과한 상태.
모노레포 / pnpm 워크스페이스
여러 패키지(core, sdk, 클라이언트 5개)를 한 저장소 안에서 함께 관리하는 방식. pnpm 워크스페이스는 그 패키지들이 서로를 로컬에서 바로 참조하고 한 번에 빌드/검사되게 해 주는 도구 설정입니다.
deprecation / archive
deprecation(폐기 예고) = "이 레포는 더 이상 관리 안 하니 새 레포로 가세요"라고 공지하는 것. archive(보관) = GitHub에서 레포를 읽기 전용으로 잠그는 것. 삭제가 아니라서 기록은 남습니다.
스캐폴딩 (scaffolding)
건물 지을 때 먼저 세우는 비계처럼, 실제 기능 전에 만드는 뼈대 — 폴더 구조, 빌드 설정, 빈 패키지 틀 같은 것들.
descriptor (기술서)
코드 대신 "이 클라이언트는 설정 파일이 여기, 형식은 TOML, 설치 명령은 이것"처럼 데이터만 적어 놓은 선언. 공통 구현 하나가 이 데이터를 읽어 manifest·설정·설치 문서를 자동 생성합니다. (ADR 0003의 핵심 개념)
스풀 (spool)
보낼 데이터를 일단 로컬에 쌓아 두는 대기열. 프린터 스풀과 같은 개념 — 네트워크가 없거나 프로세스가 곧 죽어도 데이터를 잃지 않고, 나중에 순서대로 전송합니다. 여기서는 캡처한 기억을 서버로 보내기 전 디스크에 쌓아 두는 부품입니다.
single-flight (단일 비행)
같은 작업 요청이 동시에 여러 개 들어와도 실제 실행은 한 번만 하고 나머지는 그 결과를 같이 쓰는 패턴. 여기서는 토큰 만료 시 여러 요청이 동시에 갱신을 시도해도 갱신 API 호출은 한 번만 나가게 합니다.
골든 벡터 (golden vectors)
"이 입력이면 정확히 이 출력"을 언어 중립 JSON 파일로 고정해 둔 정답지. TS 코드와 Python 코드가 같은 정답지로 테스트를 돌리므로, 두 언어 구현이 서로 어긋나면 CI가 잡아냅니다. (ADR 0002의 핵심 장치)

1. 왜 만들었나

Membase 커넥터는 원래 claude-membase, cursor-membase, hermes-membase, openclaw-membase 4개의 독립 레포로 존재했습니다. 인증, 설정 생성, 설치, 비밀값 처리 로직이 4벌로 중복됐고 — 버그 하나를 네 군데에서 고쳐야 하는 상태 — 배포·관리·GitHub 스타도 분산됐습니다. 이 레포는 그 전부를 흡수하는 단일 공개 통합 커넥터 레포입니다 (Linear 이슈 백로그: MEM-327 ~ MEM-332).

2. 핵심 설계 — ADR 0001·0002·0003

이 레포의 구조를 결정한 세 개의 ADR(Architecture Decision Record)입니다. 0001이 처음에 전체 뼈대를 정했고, 0002·0003은 그 뼈대 위에서 나중에 생긴 두 가지 구체적 문제(중복 코드, 에이전트 개수 폭증)를 각각 해결합니다.

ADR 0001 — 계층 구조와 공개 경계

계층 구조

공유 코드와 클라이언트별 코드를 엄격히 분리합니다. 위에서 아래로 "의존"하는 방향입니다 — 클라이언트 어댑터는 SDK에, SDK는 core에 기대고, 그 반대는 없습니다. 

clients/{claude,cursor,codex,hermes,openclaw}
   │  클라이언트마다 다른 부분 (설정 형식, 설치 경로)
   ▼
packages/connector-sdk
   │  어댑터가 구현해야 할 공통 인터페이스(ClientAdapter)
   ▼
packages/core
   │  인증·서버 주소·MCP 설정 생성·비밀값 가리기 (공통 로직)
   ▼
Membase Context API   ← 여기부터 서버, 비공개 영역
   ▼
private memory engine (실제 기억 저장소)

공개/비공개 경계

이 레포가 외부에 공개하는 기능(공개 계약)은 딱 4가지 + 진단입니다: remember(기억 저장) / search(기억 검색) / getContext(작업 맥락 요청) / deleteOrForget(기억 삭제). Membase 서버 내부가 기억을 어떻게 저장하고 랭킹하는지 (저장 스키마, 그래프 구조, 임베딩, 랭킹 파이프라인)는 절대 이 레포에 노출하지 않습니다. 이 경계는 사람이 리뷰로 지키는 게 아니라 pnpm check의 public-surface 가드 스크립트가 위반 시 검사를 실패시켜서 지킵니다.

ADR 0002 — 공유 capture-core

배경. 옛 레포 4개를 통합하면서 Claude· OpenClaw·Hermes 런타임을 전부 복사해 왔는데, 세 런타임에 거의 같은 로직이 3벌씩 있었습니다 — 비밀값 필터링, 캡처 큐/재시도, HTTP+OAuth 클라이언트, recall 조립.

문제였던 것. 실제로 PR 리뷰 중에 "같은 종류의 버그가 한 벌에만 있고 다른 벌엔 없는" 사례가 발견됐습니다 — 셋 중 하나만 고쳐진 채 나머지 둘은 여전히 버그를 안고 있었던 것입니다. 코드가 3벌이면 버그도 3벌이 될 수 있다는 게 실측으로 확인된 셈입니다.

고친 방법 — 세 가지 결정:

  • "무엇을"과 "언제"를 분리 — 공통 로직은 packages/capture-core 하나로 모으고, 클라이언트별 어댑터는 "언제 실행되는지"(훅 이벤트 이름·페이로드 변환)만 담당하게 했습니다. 어댑터끼리 옆으로 합치지 않고, 공통 행동은 항상 core로 내립니다.
  • 언어 정책 — 완전한 단일 언어는 불가능합니다 (OpenClaw는 TS를, Hermes는 Python을 프로세스 안에서 직접 로드하는 구조라서). TS를 서브프로세스로 감싸는 방법(Python 전용이어야 할 사용자 기기에 Node.js까지 강제 설치)과 Hermes를 MCP 전용으로 강등하는 방법(Python provider·자동 캡처 등 기존 기능을 포기) 둘 다 검토 후 기각하고, TS core 1개 + 최소한의 Python shim 1개 + 언어 중립 스펙(골든 벡터)으로 확정했습니다.

    실측 기준: TS core(packages/capture-core)가 693줄, 이를 다시 구현한 Hermes Python 쪽이 648줄로 규모가 비슷합니다. 그중 sanitize 계열(~110줄)은 골든 벡터로 TS·Python 양쪽 테스트가 같은 정답 JSON을 읽어 검증하지만, MembaseTransport에 대응하는 client.py의 토큰 갱신·401 재시도 로직(~300줄)은 아직 그런 안전망 없이 사람이 손으로 맞춘 상태입니다 — D2에서 이 부분까지 골든 벡터로 묶는 게 다음 목표입니다.

    ccxt처럼 TS를 Python으로 자동 변환(transpile)하는 방식도 검토했지만 기각했습니다: 옮겨야 할 핵심 로직 (fetch, AbortSignal, Promise 체이닝)이 트랜스파일러가 다루기 가장 어려운 런타임 API 호출 위주라 자동 변환이 안 되고 결국 손으로 다시 써야 하고, ccxt의 트랜스파일러를 그대로 가져오더라도 그 도구가 이해하는 제약적 코드 스타일에 맞춰 다시 쓰는 비용은 그대로 남습니다. ccxt는 거래소 100개 이상을 계속 추가하는 규모라 도구 투자가 남지만, 지금 옮길 대상이 클래스 하나(~300줄)뿐인 규모에서는 골든 벡터 쪽이 훨씬 쌉니다.
  • 서버로 올리기가 가장 강한 통합 — 앞의 두 결정(core 나누기, 골든 벡터)은 "코드가 두 벌인 걸 전제로 어긋나지 않게 관리하는" 방법입니다. 더 근본적인 해법은 애초에 코드를 두 벌 둘 필요가 없게 만드는 것 — 그 로직을 클라이언트가 아니라 Membase 서버 안에 두는 것입니다. 서버는 언어가 하나뿐이니, 로직이 서버에 있으면 TS/Python 어느 쪽으로도 중복될 일이 없습니다.

    그런데 모든 로직을 옮길 수 있는 건 아닙니다. 기준은 "이 작업이 사용자 기기 안에서 벌어져야만 하는 이유가 있는가"입니다.
    • 옮길 수 있는 것 — recall/context 조립(검색 결과와 프로필 정보를 모아 보기 좋은 형태로 합치는 작업)과 캡처 정규화(들어온 데이터를 서버가 이해하는 형식으로 정리하는 작업)는 어느 기기에서 실행되든 결과가 같습니다. 지금은 각 클라이언트가 검색 결과를 받아 각자 조립하는데, 이걸 서버가 이미 조립까지 끝낸 형태로 한 번에 내려주는 get_context 스타일 엔드포인트로 옮기면, "조립하는 로직"의 TS/Python 버전이 아예 필요 없어집니다 — 서버가 한 번만 만들면 5개 클라이언트가 전부 그 결과를 받아 쓰기만 하면 됩니다.
    • 못 옮기는 것 — sanitize — 비밀값을 가리는 일은 정의상 "서버로 가기 전에" 끝나야 합니다. API 키가 담긴 문장을 일단 그대로 서버에 보낸 다음 서버에서 가리면, 이미 그 순간 비밀값이 사용자 기기를 떠나 네트워크를 타고 서버 로그에 스쳐 지나간 뒤입니다 — 가리는 시점이 너무 늦습니다. 그래서 sanitize는 구조상 반드시 클라이언트 쪽에 남아야 하고, 이게 바로 TS와 Python 양쪽에 각자 존재해야 하는 이유입니다.
    • 못 옮기는 것 — 오프라인 스풀 — 스풀은 "네트워크가 끊겼거나 프로세스가 곧 죽을 때 데이터를 잃지 않게 임시로 쌓아 두는" 부품입니다(용어집 참고). 그런데 서버가 대신 이 버퍼링을 해 주려면, 애초에 서버에 연결이 돼 있어야 합니다. 기기가 오프라인인 바로 그 상황에서 서버가 대신 쌓아 줄 수 없다는 건 당연한 얘기입니다 — "연결이 안 될 때를 대비하는 부품"을 "연결이 돼야만 쓸 수 있는 곳"으로 옮기는 건 애초에 모순입니다.

ADR 0003 — 에이전트는 코드가 아니라 descriptor

배경. Membase 공식 문서는 커넥터를 "Agents 10종 + 런타임 2종(OpenClaw·Hermes)"으로 분류합니다. Agents 10종은 전부 "MCP 호스트를 mcp.membase.so에 연결 + OAuth"라는 같은 기능이고, 다른 건 설정 파일 위치·형식 같은 데이터뿐입니다.

문제였던 것. 그런데 레포는 에이전트마다 ~122줄짜리 어댑터를 손으로 쓰고 있었습니다. 실제로 cursor와 codex 두 어댑터를 줄 단위로 비교해 보니 차이는 81줄뿐이었고, 그 81줄도 전부 "동작"이 아니라 "데이터"였습니다. 이 패턴대로 나머지 8개 에이전트를 추가하면 사실상 똑같은 코드를 10벌 손으로 베끼는 셈이 됩니다.

고친 방법 — 네 가지 결정:

  • 원칙 정련 — "행동이 다르면 코드로 분리하고, 데이터만 다르면 데이터로 축약한다." 런타임 3종 (Claude·OpenClaw·Hermes)은 ADR 0001/0002대로 코드를 유지하고, 설정 전용 에이전트(나머지 7개)는 공통 구현 1개 + descriptor 데이터로 처리합니다.
  • defineMcpHostAgent(descriptor)를 connector-sdk에 추가 — descriptor 하나만 넘기면 manifest·설정·설치 문서· 스모크 테스트 선언까지 전부 자동으로 만들어 줍니다.
  • 커버리지 목표 — 문서화된 10개 에이전트 전부를 이 방식으로 커버합니다. 새 에이전트를 추가하는 작업이 "새 구현 작성"에서 "수십 줄짜리 데이터 채우기"로 바뀝니다.
  • 대량 이름 변경 없음 — 디렉터리는 clients/<id> 구조를 그대로 유지합니다. "이 에이전트가 코드 구현인지 데이터 선언인지"는 폴더를 옮겨서 표현하지 않고, runtime/ 폴더가 있는지 없는지로 표현합니다. Claude Code는 의도적 하이브리드입니다 (descriptor로 설정을 만들지만 runtime은 그대로 유지).

3. 레포 구조 — 폴더 하나씩 무슨 일을 하는지

이 레포를 처음 열면 폴더가 꽤 많은데, 사실은 2절의 계층 구조 그림(clients → connector-sdk → core → 서버)이 그대로 폴더 이름이 된 것뿐입니다. 위에서부터 하나씩 봅니다.

packages/core와 packages/connector-sdk — 모두가 기대는 바닥

packages/core는 5개 클라이언트가 전부 똑같이 필요로 하는 것들을 모아 둔 곳입니다 — "이 커넥터의 이름과 버전이 뭔지", "서버 주소가 어디인지", API 키를 실제 값이 아니라 ${MEMBASE_API_KEY}처럼 환경변수 이름으로만 다루는 방법, MCP 설정 파일을 만드는 방법, 로그에 비밀값이 찍히지 않게 가리는 방법. 클라이언트가 몇 개든 이 로직은 하나만 존재합니다.

packages/connector-sdk는 그 바로 위 계층으로, "새 클라이언트를 추가하려면 무엇을 구현해야 하는가"의 답인 ClientAdapter 인터페이스가 여기 정의돼 있습니다. 요구사항은 딱 이것뿐입니다 — "manifest를 만들어라, MCP 설정을 만들어라, 스모크 테스트 명령을 알려줘라." (8.4절에서 이 계약을 더 자세히 다룹니다.)

clients/* — 다섯 개의 실제 커넥터

여기서부터가 클라이언트마다 다른 부분입니다. 폴더 안에 runtime/이 있는지 없는지를 보면 그 클라이언트가 "실제 실행되는 프로그램을 담고 있는지, 아니면 서버에 접속하는 설정 한 조각만 갖고 있는지" 바로 구분됩니다.

  • clients/claude — runtime/ 안에 옛 레포의 플러그인 번들이 그대로 들어 있습니다: 슬래시 커맨드, 훅(세션 시작 시 자동 실행되는 스크립트), 스킬, 에이전트, 그리고 플러그인에 동봉된 stdio MCP 서버 자체까지. Claude Code는 이 서버를 사용자 기기에서 직접 실행합니다.
  • clients/cursor — 실행되는 프로그램이 없습니다. rules/skills 같은 정적 파일과, 원격 서버 https://mcp.membase.so/mcp를 가리키는 설정 조각뿐입니다.
  • clients/codex — 옛 레포가 없던, 이번 통합 과정에서 새로 추가된 클라이언트입니다. Cursor와 마찬가지로 원격 서버를 가리키는 설정뿐입니다.
  • clients/hermes — python/ 안에 Python 런타임 전체가 있습니다: provider(Hermes 호스트에 기능을 꽂는 진입점), OAuth 로그인 (사람이 브라우저로 하는 방식과, CI가 브라우저 없이 하는 client_credentials 방식 둘 다), 대화 자동 캡처, CLI, 설치 스크립트, 테스트. 이 pip 패키지가 주 실행 경로이고, 원격 MCP 설정은 보조 경로로만 곁들여 있습니다.
  • clients/openclaw — runtime/ 안에 게이트웨이 플러그인 전체: API 클라이언트, 훅, 도구(tools), 커맨드, manifest, 테스트. 이 네이티브 확장이 주 실행 경로이고, 원격 MCP 설정은 보조 경로입니다.

나머지 폴더 — 증거와 안전망

manifests/는 각 어댑터 코드가 실제로 만들어내는 manifest/MCP 설정의 "정답 사본"입니다. 리뷰어가 코드를 직접 실행하지 않고도 결과물이 어떻게 생겼는지 바로 볼 수 있게 커밋해 둔 것입니다 (그리고 4절의 가드가 "코드 결과물과 이 사본이 한 글자도 다르지 않은지" 매번 검사합니다).

smoke/와 e2e/는 5절에서 다루는 검증 하네스가 사는 곳이고, scripts/와 docs/는 4절에서 다루는 "문서 + 가드" 쌍이 사는 곳입니다.

4. 구현 방식 — 결정을 코드로도 한 번 더 강제하기

배경. 문서 하나만 믿고 규칙을 지키게 두면, 시간이 지나면서 누군가 문서를 안 읽고 규칙을 어기는 커밋을 슬쩍 넣을 수 있습니다. "커밋 리댁션을 까먹었다", "manifest 파일을 고쳤는데 예시 사본은 안 고쳤다" 같은 실수는 사람이 리뷰로 매번 잡기엔 지치는 일입니다.

고친 방법. 그래서 이 레포의 거의 모든 중요한 규칙에는 "지켜 주세요"라는 문서 옆에 "안 지키면 빌드를 실패시키는 스크립트"가 항상 짝을 이뤄 붙어 있습니다. 이 스크립트 21개를 pnpm check 한 명령으로 전부 묶어서, PR을 올릴 때마다 자동으로 다 돌립니다. 대표적인 것들을 실제로 무엇을 잡아내는지 기준으로 풀면:

check-generated-artifacts — "코드랑 예시 파일이 따로 논다"를 잡음

manifests/에는 각 어댑터가 실제로 만들어내는 결과물의 "정답 사본"이 커밋돼 있습니다(3절 참고). 이 가드는 어댑터 코드를 실제로 실행해서 나온 결과와 그 사본을 글자 단위로 비교합니다. 코드만 고치고 사본 갱신을 까먹거나, 반대로 사본만 손으로 고쳐서 실제 코드와 어긋나는 상황을 막습니다.

check-secret-hygiene — "진짜 비밀값이 커밋됐다"를 잡음

API 키 같은 값이 실제 문자열로 파일에 박혀 있으면 실패합니다. ${MEMBASE_API_KEY}처럼 "이 환경변수를 읽어라"는 참조만 허용됩니다. 진단 출력(로그, 에러 메시지)도 검사 대상이라, 일부러 가짜 비밀값을 넣어서 redaction이 실제로 그 값을 가리는지 테스트합니다.

*:native-artifacts — "옛 레포에서 옮기다 빠뜨렸다/몰래 더 옮겼다"를 잡음

클라이언트마다 native-artifacts.json이라는 목록 파일이 있고, 여기에 "옛 레포에서 무엇을 가져왔고 무엇을 아직 안 가져왔는지"가 적혀 있습니다. 이 가드는 실제 파일 트리와 이 목록을 대조합니다 — 목록에 없는 파일이 새로 생기거나, 목록엔 있는데 파일이 없으면 실패합니다.

runtime-decision-ledger — "결정 안 됐는데 된 척"을 잡음

런칭과 관련된 결정 6개(D1~D6, 예: 배포 저장소를 공개로 할지, 전송 방식을 뭘로 할지)의 현재 상태를 장부처럼 명시적으로 적어 둡니다. D1(공개 repo URL)과 D2/D3(전송·인증 방식)은 확정, D4(런타임 이전)는 완료, D6(라이브 스모크)만 테스트 계정이 없어 보류 중입니다. 코드가 "확정된 것처럼" 동작하는데 장부에는 "미확정"이라고 적혀 있으면 이 가드가 그 모순을 잡아냅니다.

packaging-action-parity — "자동화가 마음대로 배포"를 잡음

npm/PyPI/마켓플레이스에 실제로 배포하는 스위치가 꺼져 있는지 확인합니다. 재환님의 명시적 승인 없이는 이 스위치를 켜는 커밋 자체가 통과하지 못합니다 — 자동화 루프가 실수로, 혹은 누군가 무심코 "일단 배포까지 해 보자"는 코드를 넣는 사고를 막습니다.

이 다섯 개 외에도 공유 core의 계약 검사(core:contract), 공개 표면에 내부 용어가 새는지 보는 검사(public-surface, 2절의 공개/비공개 경계를 실제로 지키는 가드), 실제 Claude Code CLI로 플러그인을 검증하는 claude:plugin-parity, 문서·설치 가이드·manifest가 서로 어긋나지 않는지 보는 review-readiness, 버전 번호가 모든 곳에서 같은지 보는 version-parity, 그리고 클라이언트별 타입 검사까지 총 21개가 한 체인으로 돕니다.

5. 검증 체계 — 얕은 것부터 깊은 것까지 4겹

배경. Membase는 사용자가 API 키를 발급받아 붙여넣는 방식이 아니라 membase.so 서버에 로그인하는 방식을 씁니다. 그런데 자동 테스트(CI)는 사람이 아니라서 브라우저 로그인 화면을 띄우고 클릭할 수 없습니다. 그래서 CI 전용으로 client_credentials라는 방식 — 사람 없이 프로그램이 자체 자격증명만으로 토큰을 발급받는 OAuth 변형 — 을 씁니다.

이 인증 방식을 바탕으로, "얼마나 진짜에 가깝게 확인하는가"를 기준으로 4겹의 검증을 쌓았습니다. 아래로 갈수록 실제 서버를 더 깊이 건드리고, 그만큼 느려집니다.

스모크 (dry-run / execute) — 서버 없이, 가장 빠르게

진짜 서버에 접속하지 않고 로컬에서 끝냅니다. 어댑터가 만드는 MCP 설정이 올바른 모양인지, 비밀값이 제대로 가려지는지를 확인하고, "stub"(진짜 서버 흉내만 내는 간단한 가짜 서버)를 상대로 remember→search→context→forget이라는 공개 계약이 실제로 호출되는지 봅니다. 매번 몇 초면 끝나서 아무 때나 돌려 볼 수 있습니다.

Tier 1 — 크리덴셜 없이, 서버가 살아 있는지만

커밋된 각 클라이언트의 MCP 설정이 가리키는 서버 주소에 실제로 접속해서, 접속 자체가 되는지·MCP 스펙과 OAuth 규격을 지키는 서버가 맞는지·초기 핸드셰이크(initialize)가 도는지·응답 속도가 어떤지를 봅니다. 로그인은 필요 없습니다. Membase 서버 자체에 장애가 났을 때 그걸 "우리 코드가 깨졌다"로 오인하지 않도록 CI에서 별도 job으로 분리해 뒀습니다.

Tier 2 — 진짜 스테이징 서버에, 짧게

실제로 로그인해서(스테이징 서버 = 운영 전 단계 서버) remember와 search를 호출해 보고, 서버가 정상적으로 받아들이는지만 확인하는 수 초짜리 빠른 스모크입니다. push나 PR을 올릴 때마다 매번 CI에서 자동으로 돕니다. 외부 기여자가 올린 fork PR처럼 로그인 시크릿이 없는 경우엔 조용히 건너뜁니다.

Tier 3 — 진짜로 저장하고, 진짜로 찾아지는지

가장 깊은 검증입니다. 기억을 실제로 저장한 다음, 정말 검색으로 다시 찾아지는지(remember→recall) 확인하고, 없어야 할 게 검색에 안 걸리는지(negative case)도 봅니다. 검색 응답 속도의 백분위(p50, p95)까지 측정합니다. 저장 직후엔 검색 인덱스에 반영되는 데까지 시간이 걸릴 수 있어서 재시도 로직이 있고, 여러 번 실행해도 서로 간섭하지 않도록 실행마다 고유한 프로젝트 태그를 붙입니다. 수 분이 걸려서 매번 돌리진 않고 매일 밤 자동 실행 + 필요할 때 수동 실행합니다.

참고: 이 티어의 p95 게이트는 스테이징 서버가 오래 쉬었다가 처음 깨어날 때(콜드스타트) 일시적으로 부풀 수 있습니다 — 6절에서 실제로 이 일이 있었던 사례를 다룹니다.

이 4겹과 별개로, 복사해 온 런타임 코드 자체도 CI에서 실제로 실행됩니다 — Hermes는 Python unittest, Claude와 OpenClaw는 bun 테스트. 4절의 패리티 가드가 "필요한 파일이 다 있는지"를 본다면, 이 테스트들은 "그 코드가 실제로 돌아가는지"를 봅니다 — 서로 보완하는 다른 질문입니다.

6. 현재 상태 — 투키(two-key) 게이트 통과 완료

왜 게이트가 두 개인가. 자동 검증(CI가 초록불을 내는 것)만으로는 "이 5개 클라이언트가 실제 사람 손으로 설치했을 때도 문제없이 도는지"까지는 보장이 안 됩니다. 반대로 사람이 한 번 확인만 하고 CI가 깨진 채로 넘어가는 것도 안전하지 않습니다. 그래서 docs/north-star-readiness.md에 핵미사일 발사처럼 열쇠 두 개를 동시에 돌려야 하는 "투키 게이트"를 만들어 뒀고, 둘 다 통과해야만 다음 단계(옛 레포 폐기, 배포)로 넘어갑니다. 이 게이트를 2026-07-05에 통과했습니다(PR #13에 항목별 증거 기록).

Gate 1 ✓ 자동 검증 (기계 열쇠)

  • pnpm check + main CI 전체 그린
  • Tier 3 스테이징 E2E 그린 — 첫 실행은 콜드스타트가 부풀린 검색 p95 게이트만 실패, 재실행 그린 (재실행 우선 정책 명문화)
  • OpenClaw 라이브 게이트웨이 검증 — 이 레포의 런타임을 로드한 실제 Telegram 봇에서 검색·위키검색·위키쓰기 확인

Gate 2 ✓ 수동 서명 (사람 열쇠, Jaehwan)

  • 5개 클라이언트 전부 실사용 경로로 설치·검증: Claude Code (동봉 stdio 서버 왕복), Cursor(앱 내 왕복), Codex(관리형 OAuth + 세션 recall), Hermes(pip 설치 + OAuth + 세션 recall), OpenClaw(라이브 봇)
  • 설치 문서 대조 — 낡은 문구 2곳을 발견 즉시 수정
  • 각주 2건 수용: Hermes auto-capture는 세션 워커로만 관찰, headless client_credentials는 CI 일일 검증으로 갈음

이제 남은 것은 런칭 시퀀스 그 자체이며, 각각 별도 승인·리뷰 단위로 진행합니다: ① 릴리스 태그(버전 확정) → ② npm/PyPI/마켓플레이스 배포 → ③ 옛 레포 deprecation 공지 후 archive → ④ 로컬 작업 사본 정리. 배포는 여전히 packaging-action-parity 가드가 명시 승인 전까지 기계적으로 막고 있습니다.

공개 전환 전 점검 항목: 커밋된 AGENTS.md(에이전트 온보딩 문서)에 내부 경로·운영 세부가 있어 공개 전 다듬기 필요. 런칭과 무관한 후속 코드 작업(E2·D2·D3)은 7절 참고.

7. 지금 코드가 어디까지 와 있나 — capture-core와 descriptor

2절에서 다룬 ADR 0002(공유 capture-core)와 ADR 0003(descriptor 전환)은 둘 다 여러 단계로 나눠 진행 중입니다. 게이트 통과(6절)와 달리 이건 런칭을 막지 않는 후속 작업이라, 아직 다 끝나지 않았어도 배포에는 지장이 없습니다. 지금 딱 어디까지 왔는지만 짚습니다.

거의 다 됨 공유 capture-core

세 조각 중 두 조각(비밀값 필터링, 서버 통신 계층, 로컬 대기열)이 이미 공유 core로 옮겨져서 Claude와 OpenClaw 런타임이 실제로 그걸 가져다 쓰고 있습니다. 기존 테스트는 전부 그대로 통과합니다 — 겉보기엔 아무것도 안 바뀐 것처럼 보이지만, 안에서는 중복 코드가 하나로 합쳐진 상태입니다. 원래 계획보다 앞당겨서, 대화 캡처 시 비밀값을 가리는 정책도 OpenClaw까지 통일해 뒀습니다(보안을 이유로 먼저 처리). 남은 건 캡처 종류를 분류하는 로직 하나뿐입니다.

다음 순서: 남은 조각 마무리 → Hermes(Python)를 같은 정답 기준(골든 벡터)에 연결하고 검색어 리댁션 정책까지 통일 → Cursor·Codex에도 자동 캡처/리콜 훅을 붙여서 5개 클라이언트 전부가 같은 기반 위에서 돌게 하기.

1단계 완료 descriptor 전환

공통 구현(defineMcpHostAgent)이 만들어졌고, Cursor와 Codex 두 클라이언트가 이미 이 방식으로 전환됐습니다 — 전환 전후 결과물이 바이트 단위로 똑같다는 걸 CI가 매번 증명합니다. 코드 리뷰를 두 차례 거치면서 타입 안전성을 강화하고 안 쓰는 코드를 정리하는 수정도 반영했습니다.

다음 순서: 문서화된 나머지 8개 에이전트(ChatGPT, Gemini CLI, VS Code 등)를 같은 descriptor 방식으로 등록하고, 지금은 선언만 돼 있는 설치 방법·설정 파일 정보를 실제로 설치 문서를 자동 생성하는 데 쓰는 기능을 붙이기.

8. 인터페이스 설계 결정 — 경계마다 무엇을 계약했나

지금까지의 구현에서 확정된 인터페이스 수준의 결정들입니다. 공통 원칙은 하나입니다: 경계를 넘는 것은 데이터와 좁은 계약뿐, 구현 지식은 넘기지 않는다.

9.1 descriptor 계약 — defineMcpHostAgent<TManifest>

설치 방법을 5가지 "보기"로 못 박기

배경. Membase 공식 문서에는 연결 가능한 에이전트가 10개 나열돼 있습니다(ChatGPT, Claude Code, Codex, Cursor, Gemini CLI, VS Code 등). 연결 원리는 전부 같습니다 — "MCP 서버 주소를 알려주고 로그인 한 번". 다른 건 딱 하나, 사용자가 그 설치를 어떻게 하느냐뿐입니다.

문제였던 것. 지금 코드로 등록된 에이전트는 Cursor·Codex 2개뿐입니다. 이 2개만 보고 설치 방식의 틀(타입)을 짰다면 "명령어 실행"과 "원클릭 링크" 두 가지만 만들었을 겁니다. 그런데 ChatGPT는 웹 화면의 폼에 입력하는 방식이라 로컬에 설정 파일 자체가 없고, Poke도 마찬가지입니다. 나중에 이 둘을 추가하는 순간 타입 정의 자체를 뜯어고쳐야 했을 겁니다.

고친 방법. 코드를 쓰기 전에 문서화된 10개 에이전트 페이지를 전부 읽고 설치 방식을 분류했더니, 실제로는 5가지 패턴으로 다 들어갔습니다:

  • cli — 터미널 명령어 한 줄 (Codex, Claude Code, Gemini CLI)
  • deeplink — 대시보드에서 버튼 클릭 한 번 (Cursor, VS Code)
  • ui-form — 웹 화면의 폼 입력, 로컬 설정 파일 없음 (ChatGPT, Poke)
  • config-file — 설정 파일을 직접 열어 병합
  • manual-url — 서버 주소만 복사해서 붙여넣기 (Generic MCP URL)

이 5개를 타입스크립트의 "유니언 타입"으로 못 박았습니다 — 이 5가지 문자열 외에는 아예 코드가 컴파일되지 않게 만드는 방식입니다. 객관식 문항의 보기를 코드 레벨에서 강제하는 셈입니다.

왜 좋은가. 실제로 등록하는 건 2개뿐이지만, "보기 설계"는 10개를 다 보고 미리 끝냈습니다. 다음 단계(E2)에서 나머지 8개를 추가할 때는 이미 정해진 보기 중 하나를 고르기만 하면 되고, 타입을 다시 고칠 일이 없습니다.

manifest 작성 결과를 컴파일 시점에 검증하기

배경. 각 클라이언트는 "manifest"라는 자기소개서 파일을 만들어야 합니다. 예를 들어 Codex의 manifest는 { name, version, description, ..., mcpServers }처럼 필드 구성과 순서가 정확히 정해져 있고, CI가 "지금 커밋된 정답 파일과 한 글자도 다르면 실패"로 검사합니다.

문제였던 것. 공통 함수 defineMcpHostAgent가 이 manifest를 만들어 주는데, 처음 짠 코드는 이런 모양이었습니다: 

function generateCodexPluginManifest(config): CodexPluginManifest {
  return codexAgent.generateManifest(config) as unknown as CodexPluginManifest;
  //                                          ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
  //                                          "검사하지 말고 이 타입인 걸로 쳐줘"
}

as unknown as X는 타입스크립트에게 "일단 믿어 달라"고 우기는 문법입니다. 문제는 실제로 필드를 빼먹거나 순서를 바꿔도 컴파일러가 그대로 통과시킨다는 것 — 실수는 CI의 정답 비교 단계에 가서야, 혹은 그마저 놓치면 배포된 뒤에야 발견됩니다.

고친 방법. 함수를 "이 타입은 나중에 채워 넣을게"라는 뜻의 제네릭으로 바꿨습니다: 

function defineMcpHostAgent<TManifest>(descriptor: {
  manifest: { template: (ctx) => TManifest }
})

// 사용하는 쪽에서 실제 타입을 채워 넣음
defineMcpHostAgent<CodexPluginManifest>({ ... })

이러면 template 함수가 CodexPluginManifest 모양이 아닌 값을 반환하는 순간 그 자리에서 컴파일 에러가 납니다. 우기는 캐스트가 필요 없어집니다.

왜 좋은가. 오타나 필드 누락이 몇 달 뒤 CI에서 잡히는 게 아니라, 코드를 짜는 그 순간 에디터에서 바로 빨간 줄로 보입니다. 검증 시점이 "배포 직전"에서 "타이핑하는 중"으로 앞당겨진 것입니다.

"manifest 필수" 가드는 SDK에 한 번만

배경. Codex와 Cursor는 둘 다 manifest가 반드시 있어야 하는 클라이언트입니다. 함수가 manifest를 못 만들면 (이론상 있을 수 없는 상황이지만) 에러를 던져야 안전한데, 이 방어 코드를 두 클라이언트 모두 손으로 복붙해 넣었습니다.

문제였던 것. 지금은 2벌뿐이라 괜찮아 보이지만, E2에서 8개 에이전트가 추가되면 똑같은 방어 코드가 8번 더 복사됩니다. 나중에 이 로직을 고쳐야 할 일이 생기면 10곳을 찾아다니며 고쳐야 합니다.

고친 방법. generateRequiredManifest() 라는 메서드를 SDK(공통 라이브러리) 쪽에 딱 한 번 만들어서, 모든 클라이언트가 이 메서드 하나만 호출하게 했습니다.

왜 좋은가. 앞으로 에이전트가 몇 개가 추가되든 방어 코드의 개수는 늘지 않습니다 — 하나가 전부를 커버합니다.

아직 쓰이지 않는 필드는 "선언뿐"이라고 못 박기

배경. descriptor에는 install (설치 방법), configFile(설정 파일 위치), extras(부가 자료), requirements (요구 조건), postInstall(설치 후 할 일) 같은 필드가 있습니다.

문제였던 것. 이 필드들은 지금 당장은 아무 코드도 읽지 않습니다 — 실제로 설치 문서를 자동 생성하는 기능(E2에서 만들 렌더러)이 아직 없기 때문입니다. 주석 없이 두면, 나중에 코드를 보는 사람이 "이 필드를 채우면 뭔가 자동으로 반영되겠지"라고 오해하고 값을 넣었는데 아무 일도 안 일어나는 혼란이 생깁니다.

고친 방법. 인터페이스 정의 바로 위에 "이 필드들은 E2의 렌더러가 생기기 전까지는 선언적 문서일 뿐, 아무것도 자동 생성하지 않는다"고 명시적으로 주석을 달았습니다.

왜 좋은가. 코드가 아직 못 하는 일을 코드가 정직하게 말해 줍니다 — "여기 값을 넣어도 아직은 장식일 뿐"이라는 걸 읽는 사람이 바로 알 수 있습니다.

9.2 capture-core 계약 — 공유 런타임 프리미티브

리댁션(비밀값 가리기) 정책을 경로별로 다르게

배경. 사용자가 AI와 나눈 대화를 "기억"으로 저장할 때, 그 안에 API 키나 비밀번호가 섞여 있으면 서버로 보내기 전에 가려야 합니다([REDACTED]로 치환). 그런데 리댁션을 적용하는 곳이 두 군데입니다 — ① 대화를 기록으로 저장할 때(capture), ② 기억을 찾기 위해 검색어를 보낼 때(recall).

문제였던 것. "다 무조건 심하게 가리면 안전하지 않나?"라고 생각하기 쉽지만, 검색어까지 심하게 가리면 검색 자체가 망가집니다. 예를 들어 "내 API 토큰 만료 문제 어떻게 해결했었지"라는 검색어에서 "토큰"이라는 단어까지 지워버리면 검색 품질이 떨어집니다.

고친 방법. 경로별로 다른 세기의 정책을 정했습니다:

  • capture 경로(기기를 떠나 저장되는 텍스트) = 풀 리댁션 — 개인키·할당문(KEY=값 형태)· Bearer 토큰·CLI 비밀 플래그·주요 프로바이더 토큰까지 5종 패턴을 전부 적용. Claude가 원래 쓰던 정책이고, 이번에 OpenClaw도 이 정책으로 맞췄습니다(E1, PR #12).
  • recall 경로(검색 질의) = 좁은 리댁션 — 할당문 패턴만 지웁니다. 검색 품질을 지키려는 의도적 선택이고, 완전히 통일하는 작업은 다음 단계(D2)로 미뤄 뒀습니다.

왜 좋은가. "무조건 다 가린다"가 아니라 "무엇이 어디로 가는지"에 따라 정책 세기를 다르게 둬서, 보안과 검색 품질을 둘 다 챙깁니다.

공유 전송 계층이 "에러 모양"만은 각자에게 맡김

배경. Claude와 OpenClaw 런타임 둘 다 Membase 서버에 HTTP로 접속하고, 토큰이 만료되면 자동으로 갱신하고, 401 에러가 나면 한 번 재시도하는 로직이 필요합니다. 이 로직이 두 런타임에 거의 토씨 하나 안 틀리고 복사돼 있었습니다.

문제였던 것. 그대로 두면 나중에 버그를 고칠 때 두 곳을 따로 고쳐야 하고, 실제로 리뷰에서 "한쪽에만 있고 다른 쪽엔 없는 버그"가 발견된 적이 있습니다. 그런데 완전히 하나로 합치기엔 걸림돌이 있었습니다 — 각 런타임이 자기만의 에러 클래스(예: Claude는 ClaudeApiError)와 사용자에게 보여줄 문구를 갖고 있고, 그걸 instanceof 검사로 구분하는 코드가 이미 여기저기 있었습니다.

고친 방법. 토큰 상태 관리·동시 요청이 갱신을 중복으로 하지 않게 막는 것(single-flight)·401 시 재시도까지의 "전송 로직"만 MembaseTransport라는 공유 부품으로 뽑아내고, 에러를 만드는 함수와 메시지 문구는 각 런타임이 "주입"하는 방식으로 남겼습니다.

왜 좋은가. 버그가 잦은 어려운 부분(재시도·갱신 타이밍)은 한 곳에서만 고치면 되고, 각 런타임 고유의 instanceof 검사와 사용자 문구는 그대로 유지됩니다.

디스크 스풀은 "상태 폴더 + 리댁션 함수" 2개만 받음

배경. Claude Code의 훅은 이벤트가 생길 때마다 새 프로세스를 짧게 띄웠다 끕니다(스폰). 그 짧은 순간 안에 서버로 전송을 못 마치면 데이터를 잃어버리니, 로컬 디스크에 먼저 쌓아 두고 나중에 순서대로 보내는 "스풀"이 필요합니다.

고친 방법. 이 스풀을 capture-core로 뽑아내면서 받는 입력을 딱 2개로 제한했습니다 — 어디에 쌓을지(상태 디렉터리)와 저장 전에 어떻게 걸러낼지(sanitize 함수). 그 외의 것(무엇을 언제 보낼지 등)은 스풀이 몰라도 되게 설계했습니다.

왜 좋은가. 입력이 단순해서 다음 사용처에 바로 재사용할 수 있습니다 — Cursor도 Claude와 같은 "짧게 떴다 꺼지는 프로세스" 모델이라, D3에서 훅을 추가할 때 이 스풀을 그대로 갖다 쓰면 됩니다.

대기열(큐) 3종을 일부러 하나로 합치지 않음

배경. 캡처한 내용을 서버로 보내기 전 잠깐 대기시키는 큐가 런타임마다 다르게 구현돼 있습니다 — Claude는 디스크 스풀, OpenClaw는 인메모리 버퍼, Hermes는 개수 제한이 있는 스레드 큐.

왜 하나로 안 합쳤나. 겉보기엔 "중복 코드 3벌"처럼 보이지만, 실제로는 각 런타임이 처한 상황이 다릅니다. Claude의 훅 프로세스는 몇 초 만에 죽으니 디스크에 남겨야 하고, OpenClaw의 게이트웨이는 몇 주씩 계속 켜져 있으니 메모리 버퍼로 충분하고, Hermes는 파이썬 스레드 모델에 맞는 큐가 따로 있습니다. 이 차이를 무시하고 하나의 추상화로 억지로 묶으면, 오히려 각자에게 안 맞는 타협안이 나옵니다.

고친 방법. ADR 0002(설계 결정 문서)에 "이 3개는 우연한 중복이 아니라 의도된 차이"라고 명시적으로 적어 뒀습니다 — 나중에 누군가 "이거 왜 안 합쳤지?"라고 묻지 않도록.

골든 벡터로 TS와 Python 구현을 묶기

배경. 리댁션 로직은 TypeScript(Claude, OpenClaw)와 Python(Hermes) 두 언어로 각각 구현돼 있습니다. "같은 입력에 같은 출력이 나와야 한다"는 게 당연한 요구지만, 사람이 두 언어 코드를 매번 눈으로 비교하며 맞추는 건 실수가 나기 쉽습니다.

고친 방법. spec/sanitize-vectors.json 라는 파일에 "이 문장을 넣으면 이 결과가 나와야 한다"는 정답 목록을 언어와 무관한 JSON으로 고정해 뒀습니다. TS 테스트와 Python 테스트가 각자 이 같은 파일을 읽어서 검증합니다.

왜 좋은가. 두 언어 구현이 조금씩 어긋나기 시작해도, 몇 달 뒤 사용자가 겪는 이상한 버그로 나타나는 게 아니라 지금 당장 CI 테스트 실패로 드러납니다.

9.3 훅 등록 모델 — 클라이언트마다 "언제"가 다르다

공통 로직(capture-core)은 같지만, 그 로직을 언제 실행할지 결정하는 방식은 클라이언트마다 완전히 다릅니다 — 각 호스트 프로그램이 원래 그렇게 설계돼 있기 때문입니다.

클라이언트등록 방식이벤트와 역할
Claude Code 선언형 hooks.json — 이벤트마다 hook.cjs를 스폰(단명 프로세스) SessionStart·UserPromptSubmit (동기, recall 주입) / PostToolBatch· Stop·SessionEnd·압축 전후 (비동기, 캡처→디스크 스풀)
OpenClaw 코드 등록 api.on(...) — 장수명 게이트웨이 프로세스 안 before_agent_start(recall 주입 + 로그인 안내) / agent_end(캡처→인메모리 버퍼). 주의: 호스트 2026.6.x부터 hooks.allowConversationAccess: true 없으면 캡처 훅이 조용히 차단됨 — 라이브 검증에서 발견해 설치 문서에 반영
Hermes 훅이 아니라 provider 슬롯 — 호스트가 provider 메서드를 직접 호출 on_session_end(messages)(캡처→스레드 큐) / on_memory_write(내장 메모리 미러링) / 검색은 호스트가 provider 검색 인터페이스 호출
Cursor / Codex 현재 없음 — 순수 MCP 설정 전용 D3에서 추가 예정: Cursor는 hooks.json (Claude와 같은 스폰형이라 디스크 스풀 재사용), Codex는 plugin hook/notify. 둘 다 capture-core 위에 이벤트 이름·페이로드 변환만 하는 어댑터

OpenClaw 함정 하나 더 설명: 게이트웨이 소프트웨어가 업데이트되면서, "이 플러그인이 대화 내용에 접근해도 된다"는 허락을 명시적으로 받지 않으면 캡처 훅이 아무 에러 메시지도 없이 그냥 조용히 꺼져 있는 정책이 생겼습니다. 실제로 오늘 라이브 검증 중 이 문제를 발견해서(로그를 뒤져서 원인을 찾음), 설정에 허락 항목을 추가하고 설치 문서에도 남겼습니다.

9.4 어댑터 계약 — ClientAdapter

모든 클라이언트가 구현하는 최소 계약은 4개 멤버뿐입니다: id / displayName / generateManifest / generateMcpConfig (+ 스모크 테스트 선언). descriptor 기반 에이전트는 이 계약을 defineMcpHostAgent가 자동 생성하고, 런타임 클라이언트는 직접 구현합니다 — 즉 계약은 하나, 충족 방식이 두 가지입니다.

9.5 클라이언트별 도구·커맨드 전수 맵

"도구"는 AI가 스스로 호출하는 기능, "커맨드"는 사람이 입력하는 명령입니다. 도구가 어디서 실행되는지가 핵심 차이입니다 — 런타임 클라이언트 3종은 도구가 사용자 기기에서 돌고, Cursor·Codex는 도구가 Membase 서버에서 돌며 로컬엔 설정 한 조각만 있습니다.

클라이언트도구 (AI 호출)커맨드/스킬 (사람 입력)
Claude Code
(동봉 stdio 서버 — 로컬 실행)		 11개: add_memory · search_memory · add_wiki · search_wiki · update_wiki · delete_wiki · get_current_date · get_status · login · logout · set_project_config 커맨드 8개: /membase:login · logout · remember · recall · wiki · status · project-config · index-project
스킬 5개(remember·recall·wiki·memory-hygiene·project-context) + 큐레이터 에이전트 1개
OpenClaw
(게이트웨이 플러그인 — 로컬 실행)		 8개: membase_store · membase_search · membase_forget · membase_profile · membase_add_wiki · membase_search_wiki · membase_update_wiki · membase_delete_wiki openclaw membase login 등 CLI 서브커맨드
Hermes
(Python provider — 로컬 실행)		 8개 — OpenClaw와 동일한 이름 세트 (membase_search/store/ forget/profile + wiki 4종) hermes membase login · logout · status · resync + hermes-membase-install

이름 규칙의 이유: 런타임 클라이언트는 호스트 안에 다른 도구가 많아 membase_ 접두사로 충돌을 피하고, 원격 서버 도구는 서버가 이름 공간의 주인이라 접두사가 없습니다.

9.6 시나리오로 보는 호출 경로

시나리오 A — Telegram(OpenClaw)에서 "위키에서 X 찾아줘"

도구가 내 기기(게이트웨이)에서 실행되는 로컬 경로입니다.

사용자 → @bot "위키에서 X 찾아줘"
  ↓ Telegram provider가 메시지 수신
게이트웨이 에이전트(LLM)가 도구 선택
  ↓ membase_search_wiki 호출
clients/openclaw/runtime/src/tools/search-wiki.ts
  ↓ MembaseClient.searchWiki(...)
capture-core MembaseTransport
  · Bearer 토큰 첨부, 만료 시 single-flight 갱신 후 1회 재시도
  ↓ HTTPS
api.membase.so → 위키 검색 결과
  ↓ 포맷 → 봇 응답

(대화가 끝나면 별도로)
agent_end 훅 → sanitizeCaptureText(풀 리댁션)
  → 인메모리 버퍼 → flush → 이 대화 자체가 기억으로 저장

시나리오 B — Cursor에서 "이 내용 위키로 저장해줘"

도구가 Membase 서버에서 실행되는 원격 경로입니다. 이 레포의 기여분은 설정 파일 모양(descriptor) 뿐이라는 점이 핵심입니다.

사용자 → Cursor 채팅 "이 내용 위키로 저장해줘"
  ↓ Cursor의 MCP 클라이언트 (이 레포 코드 아님)
~/.cursor/mcp.json의 membase 항목
  · descriptor가 생성한 { url: mcp.membase.so/mcp }
  ↓ HTTPS + Cursor가 관리하는 OAuth 토큰
mcp.membase.so의 add_wiki 도구가 서버에서 실행
  ↓ 저장 완료 응답 → Cursor가 사용자에게 표시

로컬에서 실행되는 이 레포 코드: 0줄
(훅이 없으므로 자동 캡처도 없음 — D3에서 추가)

시나리오 C — 크로스 클라이언트 (게이트 검증에서 실측)

"공유 메모리"가 실제로 어떻게 성립하는지 — 2026-07-05 투키 게이트 검증에서 그대로 실행한 흐름입니다. 

[저장]  Claude Code: add_memory("...코드워드 G2-CLAUDE-7f3a...")
