Linear: Plugin/MCP 통합 레포 출시

Membase Plugin/MCP 구현 개요

흩어져 있던 4개의 클라이언트 커넥터 레포를 하나의 공개 통합 레포로 합친 과정과 현재 구현 상태를 설명합니다. 근거 문서: docs/adr/0001~0003, docs/architecture.md, docs/north-star-readiness.md.

0. 먼저 알아두면 좋은 용어

MCP (Model Context Protocol)
AI 앱(Claude, Cursor 등)이 외부 도구·데이터에 접속할 때 쓰는 표준 프로토콜. "AI용 USB 포트"라고 생각하면 됩니다. Membase가 MCP 서버가 되고, AI 클라이언트가 거기 꽂혀서 기억 저장/검색 도구를 씁니다.
커넥터 (connector) / 어댑터 (adapter)
커넥터 = "이 AI 클라이언트를 Membase에 연결해 주는 것" 전체. 어댑터 = 그중 클라이언트마다 다른 부분(설정 파일 형식, 설치 경로 등)을 담당하는 코드 조각. 콘센트 모양이 나라마다 달라서 여행용 어댑터를 끼우는 것과 같은 개념입니다.
manifest (매니페스트)
플러그인의 "자기소개서" 파일. 이름, 버전, 제공하는 기능, 실행 방법 등을 적은 JSON/YAML 문서로, 클라이언트가 이걸 읽고 플러그인을 로드합니다.
ADR (Architecture Decision Record)
"아키텍처를 왜 이렇게 정했는지"를 남기는 짧은 결정 기록 문서. 나중에 "왜 이랬더라?"를 코드가 아니라 문서에서 찾을 수 있게 합니다. 이 레포의 ADR 0001이 전체 구조를 정한 문서입니다.
smoke test (스모크 테스트)
"전원 켰을 때 연기 안 나는지" 보는 수준의 얕고 빠른 기본 동작 확인. 세세한 로직 검증이 아니라 "설정이 만들어지고, 연결되고, 기본 흐름이 도는가"만 봅니다.
E2E (end-to-end) 테스트
부품 단위가 아니라 실제 사용자 경로 전체를 처음부터 끝까지 태워 보는 테스트. 여기서는 "기억을 저장하고 → 실제 서버를 거쳐 → 검색하면 나오는가"까지 확인합니다.
parity (패리티)
"동등함". 옛 레포가 하던 것을 새 레포도 빠짐없이 똑같이 하는지 비교하는 작업. "패리티 가드"는 그 동등함이 깨지면 검사를 실패시키는 스크립트입니다.
가드 (guard)
정해 둔 규칙이 깨졌는지 자동으로 검사해서, 깨졌으면 빌드/체크를 실패시키는 스크립트. 사람이 매번 눈으로 확인하는 대신 기계가 막아줍니다.
redaction (리댁션)
로그나 진단 출력에서 비밀값(API 키 등)을 ****처럼 가려서 내보내는 것. 실수로 비밀이 화면·로그에 찍히는 사고를 막습니다.
stdio vs HTTP (MCP 전송 방식)
MCP 서버와 대화하는 두 가지 통로. stdio는 내 컴퓨터에서 프로그램을 직접 실행해 표준입출력으로 대화(로컬 실행), HTTP는 인터넷 주소로 원격 서버에 접속. 이 레포에서 Claude만 stdio(플러그인에 서버가 동봉됨)이고, Cursor·Hermes·OpenClaw의 MCP 설정은 전부 원격 HTTP (mcp.membase.so)를 씁니다.
OAuth / client_credentials
OAuth는 비밀번호를 직접 주지 않고 "허가 토큰"을 발급받는 로그인 표준. 보통 브라우저 로그인 화면이 뜹니다. client_credentials는 그중 사람 없이 프로그램(CI 등)이 자체 자격증명으로 토큰을 받는 방식 — 그래서 "브라우저 없이(headless)" 자동 테스트가 가능합니다.
CI (Continuous Integration)
코드를 push할 때마다 GitHub이 자동으로 빌드·테스트를 돌려주는 것 (여기서는 GitHub Actions). "CI 그린" = 그 자동 검사가 전부 통과한 상태.
모노레포 / pnpm 워크스페이스
여러 패키지(core, sdk, 클라이언트 5개)를 한 저장소 안에서 함께 관리하는 방식. pnpm 워크스페이스는 그 패키지들이 서로를 로컬에서 바로 참조하고 한 번에 빌드/검사되게 해 주는 도구 설정입니다.
deprecation / archive
deprecation(폐기 예고) = "이 레포는 더 이상 관리 안 하니 새 레포로 가세요"라고 공지하는 것. archive(보관) = GitHub에서 레포를 읽기 전용으로 잠그는 것. 삭제가 아니라서 기록은 남습니다.
스캐폴딩 (scaffolding)
건물 지을 때 먼저 세우는 비계처럼, 실제 기능 전에 만드는 뼈대 — 폴더 구조, 빌드 설정, 빈 패키지 틀 같은 것들.
descriptor (기술서)
코드 대신 "이 클라이언트는 설정 파일이 여기, 형식은 TOML, 설치 명령은 이것"처럼 데이터만 적어 놓은 선언. 공통 구현 하나가 이 데이터를 읽어 manifest·설정·설치 문서를 자동 생성합니다. (ADR 0003의 핵심 개념)
스풀 (spool)
보낼 데이터를 일단 로컬에 쌓아 두는 대기열. 프린터 스풀과 같은 개념 — 네트워크가 없거나 프로세스가 곧 죽어도 데이터를 잃지 않고, 나중에 순서대로 전송합니다. 여기서는 캡처한 기억을 서버로 보내기 전 디스크에 쌓아 두는 부품입니다.
single-flight (단일 비행)
같은 작업 요청이 동시에 여러 개 들어와도 실제 실행은 한 번만 하고 나머지는 그 결과를 같이 쓰는 패턴. 여기서는 토큰 만료 시 여러 요청이 동시에 갱신을 시도해도 갱신 API 호출은 한 번만 나가게 합니다.
골든 벡터 (golden vectors)
"이 입력이면 정확히 이 출력"을 언어 중립 JSON 파일로 고정해 둔 정답지. TS 코드와 Python 코드가 같은 정답지로 테스트를 돌리므로, 두 언어 구현이 서로 어긋나면 CI가 잡아냅니다. (ADR 0002의 핵심 장치)

1. 왜 만들었나

Membase 커넥터는 원래 claude-membase, cursor-membase, hermes-membase, openclaw-membase 4개의 독립 레포로 존재했습니다. 인증, 설정 생성, 설치, 비밀값 처리 로직이 4벌로 중복됐고 — 버그 하나를 네 군데에서 고쳐야 하는 상태 — 배포·관리·GitHub 스타도 분산됐습니다. 이 레포는 그 전부를 흡수하는 단일 공개 통합 커넥터 레포입니다 (Linear 이슈 백로그: MEM-327 ~ MEM-332).

2. 핵심 설계 — ADR 0001

설계 결정은 두 가지 원칙으로 요약됩니다.

계층 구조

공유 코드와 클라이언트별 코드를 엄격히 분리합니다. 위에서 아래로 "의존"하는 방향입니다 — 클라이언트 어댑터는 SDK에, SDK는 core에 기대고, 그 반대는 없습니다. 

clients/{claude,cursor,codex,hermes,openclaw}
   │  클라이언트마다 다른 부분 (설정 형식, 설치 경로)
   ▼
packages/connector-sdk
   │  어댑터가 구현해야 할 공통 인터페이스(ClientAdapter)
   ▼
packages/core
   │  인증·서버 주소·MCP 설정 생성·비밀값 가리기 (공통 로직)
   ▼
Membase Context API   ← 여기부터 서버, 비공개 영역
   ▼
private memory engine (실제 기억 저장소)

공개/비공개 경계

이 레포가 외부에 공개하는 기능(공개 계약)은 딱 4가지 + 진단입니다: remember(기억 저장) / search(기억 검색) / getContext(작업 맥락 요청) / deleteOrForget(기억 삭제). Membase 서버 내부가 기억을 어떻게 저장하고 랭킹하는지 (저장 스키마, 그래프 구조, 임베딩, 랭킹 파이프라인)는 절대 이 레포에 노출하지 않습니다. 이 경계는 사람이 리뷰로 지키는 게 아니라 pnpm check의 public-surface 가드 스크립트가 위반 시 검사를 실패시켜서 지킵니다.

3. 레포 구조

경로역할
packages/core 모든 클라이언트가 공유하는 기본 로직: 커넥터 이름/버전 같은 정체성, 서버 주소와 타임아웃, API 키를 값이 아닌 환경변수 이름(${MEMBASE_API_KEY})으로 참조하기, MCP 설정 파일 생성, 진단 출력 시 비밀값 가리기(redaction)
packages/connector-sdk 어댑터와 core 사이의 경계. 각 클라이언트 패키지가 구현해야 할 ClientAdapter 인터페이스 정의: "manifest와 MCP 설정을 만들어라, 스모크 테스트 명령을 선언해라"라는 계약
clients/claude Claude Code용 어댑터 + runtime/에 옛 레포의 플러그인 번들 전체 — 슬래시 커맨드, 훅(세션 시작 시 자동 실행되는 스크립트), 스킬, 에이전트, 그리고 플러그인에 동봉된 stdio MCP 서버와 테스트
clients/cursor Cursor용 어댑터 + rules/skills 같은 정적 파일. Cursor는 로컬 서버를 띄우지 않고 원격 HTTP MCP (https://mcp.membase.so/mcp)에 바로 접속
clients/codex OpenAI Codex CLI용 커넥터. 옛 레포가 없던, 통합 과정에서 새로 추가된 클라이언트
clients/hermes Hermes Agent용 어댑터 + python/에 Python 런타임 전체 — provider(Hermes에 기능을 꽂는 진입점), OAuth 로그인 (브라우저 없는 client_credentials 포함), 대화 자동 캡처, CLI, 설치 스크립트, 테스트. 주 실행 경로는 이 네이티브 pip 패키지이고, MCP 설정 예시는 원격 HTTP 엔드포인트를 씀
clients/openclaw OpenClaw용 어댑터 + runtime/에 플러그인 런타임 전체 — API 클라이언트, 훅, 도구(tools), 커맨드, manifest, 테스트. 주 실행 경로는 네이티브 확장이고, MCP 설정 예시는 원격 HTTP 엔드포인트를 씀
manifests/ 어댑터 코드가 생성한 plugin/MCP 설정의 "정답 예시" 사본. 리뷰어가 코드를 실행하지 않고도 결과물을 볼 수 있게 커밋해 둠
smoke/, e2e/ 공개 계약 경계만 검사하는 스모크 하네스 + 실제 스테이징 서버를 때리는 E2E 테스트
scripts/, docs/ 결정을 기록한 문서와, 그 결정이 깨지지 않는지 검사하는 가드 스크립트 쌍

4. 구현 방식 — "문서 + 가드" 쌍

이 레포의 가장 특징적인 패턴: 모든 결정을 문서로 기록하고, 그 결정이 나중에 슬그머니 어긋나지 않는지(회귀하지 않는지) 검사하는 스크립트를 pnpm check 한 명령에 전부 묶었습니다. 사람뿐 아니라 자동화 루프(스케줄에 따라 도는 codex AI)도 이 레포를 수정하기 때문에, "AI가 실수로 경계를 넘는 것"을 기계적으로 막는 구조입니다.

pnpm check는 실제로 21개 검사를 체인으로 실행합니다. 아래는 그중 대표적인 것들이고, 이 외에도 공유 core의 계약 검사 (core:contract), 공개 표면 단어 검사 (public-surface), 실제 Claude Code CLI로 플러그인을 검증하는 claude:plugin-parity, 클라이언트별 런타임 typecheck 등이 함께 돕니다.

가드검증 내용
check-generated-artifacts 커밋된 manifest/MCP 예시 파일이 어댑터 코드가 실제로 생성하는 결과와 한 글자도 다르지 않은지. 코드만 고치고 예시를 안 고치는 (또는 그 반대) 실수를 잡음
check-secret-hygiene API 키 같은 비밀값이 실제 값으로 커밋되지 않았는지 — ${MEMBASE_API_KEY} 같은 환경변수 참조만 허용. 진단 출력도 redaction을 통과하는지 가짜 비밀값으로 검사
*:native-artifacts (클라이언트별) 옛 레포에서 무엇을 가져왔고 무엇을 아직 보류 중인지를 native-artifacts.json이라는 목록 파일로 고정. "가져왔다고 착각"과 "몰래 더 가져옴"을 둘 다 방지
version-parity 버전 번호가 워크스페이스 패키지·plugin manifest·Python 메타데이터 등 모든 곳에서 동일한지
runtime-decision-ledger 런칭 관련 결정 6개(D1~D6)의 현재 상태를 장부(ledger)처럼 명시적으로 유지. 현재 D1(공개 repo URL)·D2/D3(전송·인증 방식)은 확정, D4(런타임 이전)는 완료, D6(라이브 스모크)만 테스트 계정 등이 없어 보류 중. "결정 안 됐는데 된 것처럼 진행"하는 것을 차단
packaging-action-parity npm/PyPI/마켓플레이스 배포가 Jaehwan의 명시 승인 전까지 꺼져 있음을 검증. 자동화가 임의로 외부 배포하는 사고 방지
review-readiness 필수 문서·설치 가이드·manifest·클라이언트 아티팩트가 전부 존재하고 서로 올바르게 연결돼 있는지

5. 검증 체계 — 스모크와 E2E 3티어

인증 모델: 사용자가 API 키를 직접 발급받아 붙여넣는 방식이 아니라, membase.so 서버에 로그인해서 쓰는 방식입니다. 자동 테스트는 사람이 브라우저로 로그인할 수 없으므로 client_credentials 방식(프로그램 자체 자격증명으로 토큰 발급)을 씁니다. 검증은 얕고 빠른 것부터 깊고 느린 것 순으로 4겹입니다.

  • 스모크 (dry-run/execute) — 서버 없이 로컬에서: 어댑터가 만드는 MCP 설정의 형태, 비밀값 가리기, 그리고 가짜 서버 (stub — 진짜 서버 흉내만 내는 간단한 대역)를 상대로 remember→search→context→forget 공개 계약이 도는지
  • Tier 1 (크리덴셜 불필요) — 커밋된 각 클라이언트 MCP 설정의 엔드포인트가 실제로 살아 있고 MCP 스펙·OAuth 규격을 지키는 서버인지 확인 (접속, initialize 핸드셰이크, 지연시간). Membase 서버 장애가 빌드 실패로 오인되지 않도록 CI에서 별도 job으로 분리
  • Tier 2 (스테이징 서버 + 서비스 토큰) — 진짜 스테이징 서버(운영 전 단계 서버)에 인증하고 remember/search가 받아들여지는지 보는 수 초짜리 빠른 스모크. 매 push/PR마다 CI에서 돌고, 시크릿이 없는 외부 fork PR에서는 조용히 건너뜀
  • Tier 3 (심층 품질 게이트, 수 분 소요) — 기억을 저장한 뒤 실제로 검색되는지(remember→recall), 없어야 할 게 안 나오는지(negative case), 검색 지연시간 백분위까지 확인. 저장 직후엔 검색 인덱스 반영이 늦을 수 있어 재시도와 실행별 고유 프로젝트 태그로 흔들림을 줄임. 매번 돌리기엔 느려서 매일 밤 자동 실행 + 필요 시 수동 실행

여기에 더해, 복사해 온 런타임들은 검사만 하는 게 아니라 CI에서 실제로 실행됩니다 — Hermes는 Python unittest, Claude와 OpenClaw는 bun 테스트. 패리티 가드가 "파일이 있는지"를 본다면, 이 테스트들은 "코드가 진짜 도는지"를 봅니다.

6. 통합 타임라인

  • Group A — Codex 신규 Codex CLI 커넥터 추가 (PR #2).
  • Group B — Hermes + OpenClaw 두 런타임을 통째로 복사해 오고, 각각의 테스트(Python unittest, bun 테스트)를 CI에 편입. PR 리뷰에서 나온 런타임 버그 수정 (PR #3).

  • /membase-connect 스킬 5개 클라이언트를 이 레포에서 바로 로컬 설치·연동·검증하는 대화형 셋업 스킬 추가 (PR #5). 설치 규칙을 명문화: 기존 설정을 덮어쓰지 않고 병합(백업 생성), 토큰·비밀값을 파일에 쓰지 않음(항상 OAuth 또는 환경변수), 매 클라이언트마다 검증(VERIFY) 단계로 마무리.
  • 런칭 이후 로드맵 확정 — ADR 0002 · 0003 남은 두 가지 구조적 결정을 ADR로 확정 (PR #6). 아래 8절 참고. 둘 다 런칭(투키 게이트)을 막지 않는 이후 작업이며, 서로 독립적이라 어느 쪽이 먼저 진행돼도 됩니다.
  • Group D1 — capture-core 추출 완료 3개 slice로 분할 머지 (PR #7~#9): ① sanitize + 골든 벡터, ② MembaseTransport(OAuth 갱신·재시도), ③ 디스크 캡처 스풀. Claude·OpenClaw 런타임이 공유 core를 import하고 기존 테스트는 무변경 통과. 남은 D1 항목은 capture kinds 하나.

  • Group E1 — descriptor 메커니즘 defineMcpHostAgent 구현 + cursor/codex를 descriptor로 이행(골든 바이트 동일성 CI 증명) + OpenClaw 캡처 경로 시크릿 리댁션을 capture-core로 조기 수렴 (PR #12). 8각도 코드리뷰 2라운드를 거쳐 제네릭 타입 강화·죽은 코드 제거 등 리뷰 수정 반영.
  • 투키 게이트 통과 — 런칭 자격 확보 Gate 1(자동 4항목)과 Gate 2(수동 5클라이언트 실사용 검증)를 모두 통과하고 증거와 함께 문서화 (PR #13). 핵심 증거: 센티널 기억 하나를 Claude Code로 저장 → Cursor·Codex·Hermes·OpenClaw 전부에서 검색 성공 — "공유 메모리" 명제의 5클라이언트 실증.

공개 전환 전 점검 항목: 커밋된 AGENTS.md(에이전트 온보딩 문서)에 내부 경로·운영 세부가 있어 공개 전 다듬기 필요. 런칭과 무관한 후속 코드 작업(E2·D2·D3)은 8절 참고.

8. 런칭 이후 로드맵 — ADR 0002 / 0003

ADR 0002 — 공유 capture-core (Group D)

Group B/C로 복사해 온 3개 런타임(Claude·OpenClaw는 TS, Hermes는 Python)에는 같은 로직이 3벌 존재합니다 — 비밀값 필터링, 캡처 큐/재시도, HTTP+OAuth 클라이언트, recall 조립. PR #3 리뷰에서 실제로 "같은 종류의 버그가 한 벌에만 있고 다른 벌엔 없는" 비용이 확인됐습니다. 결정:

  • "무엇을"과 "언제"를 분리 — 공통 로직은 packages/capture-core 하나로, 클라이언트별 어댑터는 "언제 실행되는지"(훅 이벤트 이름·페이로드 변환)만 담당. 어댑터끼리 옆으로 합치지 않고, 공통 행동은 항상 core로 내림.
  • 언어 정책 — 완전한 단일 언어는 불가능 (OpenClaw는 TS를, Hermes는 Python을 프로세스 안에서 직접 로드). TS 서브프로세스 shim·MCP 전용 강등·Python 단일화를 모두 검토 후 기각하고, TS core 1개 + 최소 Python shim 1개 + 언어 중립 스펙(골든 벡터)으로 확정.
  • 서버로 올리기가 가장 강한 통합 — 사용자 기기에서 돌 필요 없는 것(recall/context 조립, 캡처 정규화)은 Membase 서버로 이전. 단 sanitize(비밀값은 기기를 떠나기 전에 걸러야 함)와 오프라인 스풀은 절대 서버로 못 올림.

진행: D1 사실상 완료 (slice 1~3 머지, capture kinds만 잔여). 캡처 경로 리댁션 수렴은 원래 D2 계획이었으나 보안 우선으로 E1에서 조기 반영. 남은 단계: D1 잔여 → D2(골든 벡터에 Hermes 연결 + shim 축소 + recall 경로 리댁션 수렴) → D3(Cursor·Codex 훅 어댑터 — 자동 캡처/리콜이 5개 클라이언트 전부에 도달).

ADR 0003 — 에이전트는 코드가 아니라 descriptor (Group E)

공식 문서(docs.membase.so)에 커넥터는 "Agents 10종 + 런타임 2종(OpenClaw·Hermes)"으로 분류되는데, Agents 10종은 전부 "MCP 호스트를 mcp.membase.so에 연결 + OAuth"라는 같은 기능이고 차이는 설정 파일 위치·형식 같은 데이터뿐. 그런데 레포는 에이전트마다 ~122줄짜리 어댑터를 손으로 쓰고 있었고(cursor·codex 두 어댑터의 실측 차이는 81줄, 전부 데이터), 이대로면 10벌 복사가 됩니다. 결정:

  • 원칙 정련 — "행동이 다르면 코드로 분리, 데이터만 다르면 데이터로 축약". 런타임 3종은 ADR 0001/0002대로 코드 유지, 설정 전용 에이전트는 공통 구현 1개 + descriptor.
  • defineMcpHostAgent(descriptor)를 connector-sdk에 추가 — descriptor 하나로 manifest·설정·설치 문서·스모크 선언을 전부 렌더링.
  • 커버리지 목표 — 문서화된 10개 에이전트 전부(현재 2개 → ChatGPT, Gemini CLI, VS Code 등 8개 추가). 각각 수십 줄짜리 descriptor + e2e 설정 항목이면 끝.
  • 대량 이름 변경 없음 — 디렉터리는 clients/<id> 유지. 계층은 폴더 이동이 아니라 "runtime/ 폴더가 있느냐"로 표현. Claude는 의도적 하이브리드 (descriptor 어댑터 + runtime 유지).

진행: E1 완료 (PR #12 — cursor/codex 이행, 골든 바이트 동일성 CI 증명). 남은 단계: E2(나머지 에이전트 descriptor 등록 + install-doc 렌더러 — 지금은 선언만 있는 descriptor 필드들을 실제로 소비하게 만드는 단계).

9. 인터페이스 설계 결정 — 경계마다 무엇을 계약했나

지금까지의 구현에서 확정된 인터페이스 수준의 결정들입니다. 공통 원칙은 하나입니다: 경계를 넘는 것은 데이터와 좁은 계약뿐, 구현 지식은 넘기지 않는다.

9.1 descriptor 계약 — defineMcpHostAgent<TManifest>

결정내용과 이유
설치 방법은 5종 유니언 타입 문서화된 10개 에이전트 전수 조사에서 도출: cli(명령어) / deeplink(원클릭) / ui-form(호스티드 폼, 설정 파일 없음) / config-file(수동 병합) / manual-url(URL 붙여넣기). 스키마를 2개 사례가 아니라 10개 기준으로 먼저 설계해 E2에서의 스키마 개정을 방지
manifest template은 제네릭으로 컴파일 검증 TManifest 타입 파라미터로 template 반환값이 각 클라이언트의 manifest 인터페이스와 일치함을 컴파일러가 강제. 골든 바이트 검증(CI)에 도달하기 전에 타입에서 먼저 잡힘 — 리뷰에서 as unknown as 캐스트를 걷어낸 결과
generateRequiredManifest()는 SDK에 한 번만 "manifest가 반드시 있는 클라이언트"의 throw 가드를 클라이언트마다 복붙하지 않고 SDK 메서드 하나로 제공. E2에서 에이전트가 늘어도 가드는 늘지 않음
manifest 외 필드는 아직 선언만 (명시적) install·configFile· extras·requirements· postInstall은 E2의 install-doc 렌더러가 소비할 때까지 "선언적 문서"임을 인터페이스 주석에 명시 — 읽는 사람이 load-bearing으로 오해하지 않게

9.2 capture-core 계약 — 공유 런타임 프리미티브

결정내용과 이유
리댁션 정책 2단계 capture 경로(기기를 떠나는 텍스트) = 풀 리댁션 (redactSecrets: 개인키·할당문·bearer·CLI 플래그·프로바이더 토큰 5종 패턴) — Claude 정책으로 전 클라이언트 수렴, E1에서 OpenClaw까지 완료. recall 경로(검색 질의) = 좁은 할당문 리댁션 — 질의를 과하게 지우면 검색 품질이 떨어지므로 D2에서 의도적 수렴 예정. "전부 리댁션"이 아니라 경로별 정책이라는 게 결정의 핵심
MembaseTransport는 에러를 주입받음 토큰 상태·single-flight 갱신(동시 요청이 갱신을 한 번만 수행)·401 시 1회 재시도는 core가 소유하되, 에러 클래스와 메시지 문구는 각 런타임이 주입 — instanceof 검사와 사용자 향 문구를 깨지 않고 전송 계층만 공유
디스크 스풀은 파라미터 2개짜리 계약 상태 디렉터리 + sanitize 함수만 받는 파일락 스풀. Claude처럼 훅이 단명 프로세스인 클라이언트용이며, D3의 Cursor 훅(같은 스폰 모델)이 그대로 재사용할 예정
큐 3종은 일부러 통합하지 않음 디스크 스풀(Claude — 단명 스폰 프로세스) / 인메모리 버퍼 (OpenClaw — 장수명 게이트웨이) / bounded 스레드 큐(Hermes — Python 호스트)는 우연한 중복이 아니라 실행 모델의 차이. 하나의 추상화로 강제하지 않기로 ADR 0002 slice 3에서 명시 결정
골든 벡터가 언어 경계를 묶음 spec/sanitize-vectors.json — 입력→출력 정답을 언어 중립 JSON으로 고정, TS 테스트와 Python 테스트가 같은 파일을 소비. 두 언어 구현의 드리프트가 몇 달 뒤 버그가 아니라 지금 CI 실패로 나타남

9.3 훅 등록 모델 — 클라이언트마다 "언제"가 다르다

클라이언트등록 방식이벤트와 역할
Claude Code 선언형 hooks.json — 이벤트마다 hook.cjs를 스폰(단명 프로세스) SessionStart·UserPromptSubmit (동기, recall 주입) / PostToolBatch· Stop·SessionEnd·압축 전후 (비동기, 캡처→디스크 스풀)
OpenClaw 코드 등록 api.on(...) — 장수명 게이트웨이 프로세스 안 before_agent_start(recall 주입 + 로그인 안내) / agent_end(캡처→인메모리 버퍼). 주의: 호스트 2026.6.x부터 hooks.allowConversationAccess: true 없으면 캡처 훅이 조용히 차단됨 — 라이브 검증에서 발견해 설치 문서에 반영
Hermes 훅이 아니라 provider 슬롯 — 호스트가 provider 메서드를 직접 호출 on_session_end(messages)(캡처→스레드 큐) / on_memory_write(내장 메모리 미러링) / 검색은 호스트가 provider 검색 인터페이스 호출
Cursor / Codex 현재 없음 — 순수 MCP 설정 전용 D3에서 추가 예정: Cursor는 hooks.json (Claude와 같은 스폰형이라 디스크 스풀 재사용), Codex는 plugin hook/notify. 둘 다 capture-core 위에 이벤트 이름·페이로드 변환만 하는 어댑터

9.4 어댑터 계약 — ClientAdapter

모든 클라이언트가 구현하는 최소 계약은 4개 멤버뿐입니다: id / displayName / generateManifest / generateMcpConfig (+ 스모크 테스트 선언). descriptor 기반 에이전트는 이 계약을 defineMcpHostAgent가 자동 생성하고, 런타임 클라이언트는 직접 구현합니다 — 즉 계약은 하나, 충족 방식이 두 가지입니다.

9.5 클라이언트별 도구·커맨드 전수 맵

"도구"는 AI가 스스로 호출하는 기능, "커맨드"는 사람이 입력하는 명령입니다. 도구가 어디서 실행되는지가 핵심 차이입니다 — 런타임 클라이언트 3종은 도구가 사용자 기기에서 돌고, Cursor·Codex는 도구가 Membase 서버에서 돌며 로컬엔 설정 한 조각만 있습니다.

클라이언트도구 (AI 호출)커맨드/스킬 (사람 입력)
Claude Code
(동봉 stdio 서버 — 로컬 실행)		 11개: add_memory · search_memory · add_wiki · search_wiki · update_wiki · delete_wiki · get_current_date · get_status · login · logout · set_project_config 커맨드 8개: /membase:login · logout · remember · recall · wiki · status · project-config · index-project
스킬 5개(remember·recall·wiki·memory-hygiene·project-context) + 큐레이터 에이전트 1개
OpenClaw
(게이트웨이 플러그인 — 로컬 실행)		 8개: membase_store · membase_search · membase_forget · membase_profile · membase_add_wiki · membase_search_wiki · membase_update_wiki · membase_delete_wiki openclaw membase login 등 CLI 서브커맨드
Hermes
(Python provider — 로컬 실행)		 8개 — OpenClaw와 동일한 이름 세트 (membase_search/store/ forget/profile + wiki 4종) hermes membase login · logout · status · resync + hermes-membase-install
Cursor · Codex
(원격 HTTP MCP — 서버 실행)		 서버가 노출하는 7개: add_memory · search_memory · add_wiki · search_wiki · update_wiki · delete_wiki · get_current_date (Tier 3 계약 게이트가 7/7 존재를 매일 검증) 없음 — 로컬엔 훅도 커맨드도 없고 MCP 설정뿐 (D3에서 훅 어댑터 추가 예정)

이름 규칙의 이유: 런타임 클라이언트는 호스트 안에 다른 도구가 많아 membase_ 접두사로 충돌을 피하고, 원격 서버 도구는 서버가 이름 공간의 주인이라 접두사가 없습니다.

9.6 시나리오로 보는 호출 경로

시나리오 A — Telegram(OpenClaw)에서 "위키에서 X 찾아줘"

도구가 내 기기(게이트웨이)에서 실행되는 로컬 경로입니다.

사용자 → @bot "위키에서 X 찾아줘"
  ↓ Telegram provider가 메시지 수신
게이트웨이 에이전트(LLM)가 도구 선택
  ↓ membase_search_wiki 호출
clients/openclaw/runtime/src/tools/search-wiki.ts
  ↓ MembaseClient.searchWiki(...)
capture-core MembaseTransport
  · Bearer 토큰 첨부, 만료 시 single-flight 갱신 후 1회 재시도
  ↓ HTTPS
api.membase.so → 위키 검색 결과
  ↓ 포맷 → 봇 응답

(대화가 끝나면 별도로)
agent_end 훅 → sanitizeCaptureText(풀 리댁션)
  → 인메모리 버퍼 → flush → 이 대화 자체가 기억으로 저장

시나리오 B — Cursor에서 "이 내용 위키로 저장해줘"

도구가 Membase 서버에서 실행되는 원격 경로입니다. 이 레포의 기여분은 설정 파일 모양(descriptor) 뿐이라는 점이 핵심입니다.

사용자 → Cursor 채팅 "이 내용 위키로 저장해줘"
  ↓ Cursor의 MCP 클라이언트 (이 레포 코드 아님)
~/.cursor/mcp.json의 membase 항목
  · descriptor가 생성한 { url: mcp.membase.so/mcp }
  ↓ HTTPS + Cursor가 관리하는 OAuth 토큰
mcp.membase.so의 add_wiki 도구가 서버에서 실행
  ↓ 저장 완료 응답 → Cursor가 사용자에게 표시

로컬에서 실행되는 이 레포 코드: 0줄
(훅이 없으므로 자동 캡처도 없음 — D3에서 추가)

시나리오 C — 크로스 클라이언트 (게이트 검증에서 실측)

"공유 메모리"가 실제로 어떻게 성립하는지 — 2026-07-05 투키 게이트 검증에서 그대로 실행한 흐름입니다. 

[저장]  Claude Code: add_memory("...코드워드 G2-CLAUDE-7f3a...")
        → 동봉 stdio 서버(mcp-server.cjs) → api.membase.so
        → 인덱싱 (~30초 소요, Tier 3가 이 지연도 측정)

[검색]  네 갈래가 전부 같은 기억에 도달:
  Cursor  → mcp.membase.so의 search_memory (원격 도구)
  Codex   → mcp.membase.so의 search_memory (원격 도구)
  Hermes  → provider의 membase_search → 로컬 클라이언트 → API
  OpenClaw→ membase_search 도구 → 로컬 클라이언트 → API

같은 계정 + 같은 서버 = 어느 문으로 들어가도 같은 기억.
클라이언트가 다섯이어도 기억 저장소는 하나라는 것이
이 레포가 제공하는 제품 명제의 전부입니다.
